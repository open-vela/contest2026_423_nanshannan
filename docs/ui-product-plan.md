# K7 界面重新规划：桌面家庭中控 + 端侧工作健康助手

> 状态：规划稿（2026-10-30），未实现。本文所有"可行/不可行"判断都附了依据；
> 标"待实测"的数字必须先在板上测出来，再决定是否进入开发。

## 1. 产品定位

**一句话**：放在书桌上的 5 寸竖屏设备。居家办公或学习的人用它控制家里的灯、空调、窗帘，
同时它在本地看着"人还在不在座位上、坐了多久、该不该休息"，到点提醒。

为什么是"桌面"而不是"墙面"：

- 屏是 5 寸 720x1280 竖屏，摄像头要正对使用者的脸。墙装中控（如 Aqara Panel S1 Plus）
  是全家共享、远距离操作，而工作助手是个人、近距离，两者只有在**书桌**这个位置上能合到一台设备里。
- 因此家居控制按"我在书房顺手控制全屋"来设计：常用场景一键，不追求墙面中控那种完整的房间管理。

目标用户：居家办公者、学生。演示场景：书房一张桌子。

## 2. 现实约束（来自本仓已验证的事实）

| 条件 | 现状 | 对规划的影响 |
|---|---|---|
| 屏幕/触摸 | 5 寸 720x1280 MIPI，FT8756 触摸，已验证 | 竖屏布局；底部导航；大按钮 |
| 摄像头 | IMX415，`/dev/video0`，相机页约 30fps，已验证 | 30fps 够看眨眼（一次眨眼 100–400ms ≈ 3–12 帧） |
| 音频 | ES8388 录放音、喇叭，已验证 | 语音提醒、TTS 播报可用 |
| 云端大模型 | mimo-v2.5 视觉问答实测 4.5–27s/次 | **只能做"按一下问一次"**，不能做持续监测 |
| NPU | 只在 Linux 侧有（librknnrt），AMP 共享内存方案已设计，**未端到端验证** | 持续感知的算力来源是最大风险，必须先测 |
| 网络 | 以太网、WiFi（WPA2 + DHCP）已验证 | 家居控制走局域网 |
| 红外接收 | 驱动已写（PWM0 + NEC，`/dev/lirc0`），**未上板** | 可用遥控器操作界面（方向键/确定） |
| 红外发射 | 板上没有发射管 | **不能直接遥控空调电视**，需外接或走网关 |
| Zigbee/Thread | 无射频 | 不能当 Zigbee 网关 |
| 家居协议库 | apps 里有 `mqttc`/`paho_mqtt`、`connectedhomeip`（Matter），均未启用 | MQTT 对接 Home Assistant 最现实；Matter 列为远期 |
| 中文字库 | GB2312 一级 + 常用符号（3888 字形） | 界面用字要过 `scripts/check-ui-glyphs.py` |

## 3. 功能调研与取舍

### 3.1 久坐检测 —— 首期做

- **真实产品**：Apple Watch 的站立提醒是每小时一次，每小时站立活动满 1 分钟算达标；
  间隔不能自定义，用户有抱怨（[MacRumors](https://www.macrumors.com/how-to/turn-off-time-to-stand-reminders-apple-watch/)、
  [Apple 社区](https://discussions.apple.com/thread/255096508)）。
- **做法**：摄像头只做"座位上有没有人脸"（人脸检测，不识别是谁）。连续在座计时；离座超过 2 分钟才算休息过、计时清零，
  免得低头捡东西被误判成离座。默认 45 分钟提醒，可调 30/45/60/90。
- **为什么可行**：人在不在是视觉里最稳的信号，对光照和角度的要求远低于眨眼。
- **降级**：摄像头关闭时改用纯计时，加"我起来了"按钮，功能不断。

### 3.2 用眼休息（20-20-20）—— 首期做

- **依据**：美国眼科学会（AAO）建议每 20 分钟看 6 米（20 英尺）外至少 20 秒；正常眨眼约 15 次/分钟，
  看屏幕时会减半（[Drugs.com 转述 AAO](https://Drugs.com/news/screens-everywhere-resolve-protect-your-vision-116714.html)、
  [Medical News Today](https://www.medicalnewstoday.com/articles/321536)）。
  后者也指出这条规则本身缺少严格研究，所以界面上写"建议"，不写"医学要求"。
- **做法**：复用 3.1 的在座计时，只是周期更短、提醒更轻（屏幕角标 + 一声提示音，不弹全屏）。

### 3.3 眨眼频率 / 疲劳 —— 二期，前提是算力实测通过

- **业界做法**：用人脸关键点算眼睛纵横比（EAR），低于阈值算闭眼；疲劳看 PERCLOS（一段时间内闭眼时间占比）。
- **已知局限**：光太暗或太亮、侧脸、戴眼镜、遮挡都会让关键点不准；EAR 一般不区分正常眨眼和瞌睡，
  也看不到打哈欠、点头；每个人眨眼频率本来就不一样
  （[PMC 综述](https://pmc.ncbi.nlm.nih.gov/articles/PMC10108649/)、
  [arXiv 2511.13618](https://arxiv.org/pdf/2511.13618)、
  [Optalert](https://www.optalert.com/?p=1500)）。
- **产品化取舍**：
  - 只报**趋势**（"最近 10 分钟眨眼明显少于你平时"），不报"你疲劳了"这种诊断。
  - 基线按人校准：每个使用者前几天的中位数当"平时"，不用文献里的固定值。
  - 置信度门控：脸不正、太暗、检测不到眼睛时，这段数据直接丢弃，界面显示"光线不足，暂停统计"。
- **前提**：要有关键点模型稳定跑到 15fps 以上。RK3576 的 NPU 上 YOLOv8n（640x640）实测约 35fps
  （[Seeed 基准](https://sensecraft.seeed.cc/ai-lab/en/projects/9)），小尺寸人脸关键点模型应该更快，
  但**没有找到 RK3576 上的公开实测数据**，要自己测。另外 NPU 在本项目里只能走 Linux 侧，这条链路还没打通。

### 3.4 坐姿 / 离屏距离 —— 二期

- **做法**：单目摄像头用人脸框大小和位置估算前倾、低头：脸框变大说明靠近，脸框下移说明低头。
  需要用户先坐正校准一次。只提示"离屏幕太近"，不做精确测距。
- **依据**：AAO 建议屏幕离眼约 64cm（一臂远）、视线略向下（同 3.2 的来源）。

### 3.5 喝水 —— 不做视觉识别，改成提醒 + 记录

- **真实产品**：HidrateSpark 智能水杯是靠杯底传感器记每一口，蓝牙同步到 App；
  它的 App 不配杯子也能用，靠手动记录（[HidrateSpark](https://hidratespark.com/pages/how-it-works)、
  [Reviewed](https://reviewed.com/features/hidrate-spark-3-smart-water-bottle-review)）。
  市面上没有靠桌面摄像头认"喝水动作"的成熟产品。
- **为什么不用摄像头**：杯子挡脸、角度、杯型都会影响，误报漏报都很高。动作识别还得另跑一个模型，和 3.3 抢算力。
- **做法**：定时提醒（默认 60 分钟），提醒卡片上一键"喝了"或语音说"我喝水了"记一杯，首页显示今日进度。
  桌面守护已有的"水杯还在不在"（云端视觉）可以当可选的辅助提示，但不算作记录。

### 3.6 面部微表情识别 —— 建议不做

理由有三个，任何一个都足以放弃：

1. **技术上不成立**：微表情研究的标准数据集 CASME II 用 200fps 高速摄像头在实验室录制，
   原作者基线准确率约 63%，后续方法在同一数据集上报 70%–75%，受过训练的专家肉眼约 47%
   （[arXiv 2602.23950](https://arxiv.org/pdf/2602.23950)、[arXiv 2503.21690](https://arxiv.org/pdf/2503.21690)）。
   本板 30fps，环境不受控，结果不可信。
2. **法规风险**：欧盟 AI 法案第 5(1)(f) 条禁止在工作场所和教育机构用 AI 推断人的情绪，
   只对医疗和安全用途例外；官方指南明确"一般健康福祉"不算例外
   （[FPF 解读](https://fpf.org/blog/red-lines-under-eu-ai-act-unpacking-the-prohibition-of-emotion-recognition-in-the-workplace-and-education-institutions/)、
   [Lewis Silkin](https://www.lewissilkin.com/insights/2025/02/17/understanding-the-eu-ai-acts-prohibited-practices-key-workplace-and-advertising-102k011)）。
   "工作助手 + 情绪识别"正好落在这条红线上。
3. **用户反感**：让一台设备评判"你现在的情绪"，比提醒休息更容易被关掉。

**替代**：可做"心情打卡"，由用户自己点一个表情，和专注时长放在一起看。数据是用户主动给的，不是推断的。

## 4. 隐私设计（硬性要求，不是可选项）

依据：人脸信息属于《个人信息保护法》的敏感个人信息，处理要取得**单独同意**；相关解读认为，
人脸信息原则上应存在设备内、不经互联网对外传输；国家标准也要求非必要时优先用非生物识别方案
（[安全内参](https://www.secrss.com/articles/76980)、[观韬](https://guantao.com/page2208)）。

- 首次开启"座位感知"时单独弹出同意页，写清楚：只在本机判断有没有人、不存图片、不上传。不同意也能用纯计时版。
- 持续感知**只在本地**跑。只有用户按"看一看"时才拍一张发给云端，并在界面上明示"将上传一张照片"。
- 摄像头工作时状态栏常驻图标；首页一键关闭摄像头，关了就真停采集（停 V4L2 流），不只是不显示。
- 只保存聚合统计（每小时在座分钟数、休息次数），不保存帧和人脸特征。

## 5. 界面结构（720x1280 竖屏）

现在的页签"双核 / 设备 / 曲线 / 助手 / 音视频 / 关于"是工程验证页，产品化后全部收进"设置 → 开发者"，给评审展示技术深度时再打开。

底部导航 4 项：

```
┌──────────────────────────┐
│ 10:42   🌡26°  📷●  📶     │  状态栏：时间、室温（来自 HA）、摄像头指示、网络
├──────────────────────────┤
│                          │
│        （当前页）         │
│                          │
├──────┬──────┬──────┬──────┤
│ 今日 │ 家居 │ 助手 │ 设置 │
└──────┴──────┴──────┴──────┘
```

| 页 | 内容 |
|---|---|
| **今日**（首页） | 大时钟；在座计时环（"已坐 38 分钟，7 分钟后提醒"）；今日喝水进度；4 个场景按钮（专注 / 休息 / 回家 / 离家）；语音入口 |
| **家居** | 按房间分组的设备卡片（灯、空调、窗帘、插座），点卡片开关，长按调亮度、温度；数据来自 Home Assistant |
| **助手** | 上半屏：专注计时（番茄钟）和今日统计（在座时长、休息次数、眨眼趋势〔二期〕）；下半屏：现有的 AI 对话和"看一看" |
| **设置** | 网络、提醒间隔、座位感知开关与同意记录、音量、**开发者**（原有工程页） |

另外两种状态：

- **待机屏**：一段时间无操作后转成大字时钟 + 下一次提醒时间，降低亮度。检测到有人坐下时亮屏
  （参照 Aqara S1 Plus 有人靠近才亮屏的做法，[来源](https://www.varle.lt/ismanios-oru-stoteles/aqara-panel-hub-s1-plus--42674254.html)）。
- **提醒卡片**：全屏卡片 + 语音一句话，三个按钮："好的" / "10 分钟后" / "今天不再提醒"。
  连续 3 次点"10 分钟后"就降一档频率，不跟用户较劲。

输入方式：触摸为主，红外遥控（方向键 + 确定）为辅，后者经 LVGL 键盘输入设备和焦点组实现，让人离开座位也能操作。

## 6. 系统架构

```
 摄像头 ─▶ 感知服务（独立任务，有界、可关）─▶ 事件：在座/离座、脸框、眨眼
                    │                                  │
             算力：A. Linux NPU（共享内存）            ▼
                   B. A53 上跑小模型（降级）       提醒调度（计时、阈值、冷却）
                                                        │
 Home Assistant ◀─ MQTT ─▶ 家居服务 ──────────────▶ LVGL 界面 ◀─ 触摸 / 红外遥控
                                                        │
                                              云端 mimo（仅用户主动触发）
```

- 感知服务和界面分开，界面只订阅事件。感知卡住时界面不受影响，提醒退回纯计时。
- 家居控制首选 **MQTT 对接 Home Assistant**：现成的 `mqttc` 库可用，HA 把各家的设备统一成一套接口。
  Matter（`connectedhomeip`）协议正确，但在 NuttX 上体积大、未验证，列为远期。

## 7. 分期与验收

| 期 | 内容 | 通过标准 |
|---|---|---|
| **P0 界面重构** | 底部 4 页框架；工程页迁入开发者；今日页（纯计时版久坐、喝水记录）；提醒卡片；红外遥控导航 | 连续运行 8 小时，提醒按时出现；点按响应 < 100ms；所有中文过字库检查 |
| **P1 座位感知** | 先测算力：A53 与 NPU 各跑一个人脸检测，记录帧率；选一条路接入在座/离座；同意页和摄像头开关 | 正常光、背光、暗光各测 30 分钟，误判离座 < 1 次/30 分钟；关掉摄像头后 V4L2 确实停流 |
| **P2 家居** | MQTT 接 HA；家居页设备卡片；场景按钮 | 开关指令 1 秒内生效；HA 断开时界面显示"离线"，不假装成功 |
| **P3 用眼与坐姿** | 关键点模型；眨眼趋势；离屏太近提示 | 先测关键点模型帧率 ≥ 15fps 才立项；低置信度数据被丢弃并显示原因 |
| 不做 | 微表情识别；摄像头识别喝水 | — |

## 8. 待确认

1. 演示时有没有一台 Home Assistant（或其他 MQTT 网关）和几个真实设备？没有的话，P2 改为本地模拟设备，并在界面上标明"演示数据"。
2. 算力路线优先级：先打通 Linux NPU（收益大、风险大），还是先在 A53 上跑一个小人脸检测（能保底）？
3. 是否需要多用户？如果需要，"基线按人校准"就要区分谁在用。不做身份识别的话，就只能按设备算一个基线。
