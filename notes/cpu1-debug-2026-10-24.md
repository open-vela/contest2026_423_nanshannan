# CPU1 双系统不接任务：外部调试接口尝试（2026-10-24）

背景见 HANDOFF 7.2。本轮想不重编镜像，从 CPU0 经 CoreSight 读 CPU1 的
PC 采样（EDPCSR），直接看 CPU1 停在哪里。

## 已确认的地址（只读访问安全）

TRM Part1 9.1.2：调试组件 `DAP_ROM = 0x22800000`（A72 再加 0x400000），
落在 openvela 的 DEVICE_REGION（0x20000000 + 192MB）内。

ROM 表 0x22800000 有 16 项，偏移 0x10000..0x1f000，每项 4KB。按 DEVTYPE
（0xFCC）判读：0x15 = 处理器调试，0x16 = PMU，两两交替：

| A53 核 | 调试块 | PMU |
|---|---|---|
| core0 | 0x22810000 | 0x22811000 |
| core1 | 0x22812000 | 0x22813000 |
| core2 | 0x22814000 | 0x22815000 |
| core3 | 0x22816000 | 0x22817000 |

EDPRSR（+0x314）读回：core0 = 0x0b；core1/2/3 = 0x2ab。
0x2ab = PU、SPD、SR、**OSLK**、EDAD、EPMAD。core1 和 core2/3 相同，
所以 OS Lock 本身解释不了“只有 CPU1 有问题”。

core0 的 EDPCSR（+0x0a0）读回 0x4a438cc0、高位 0。

## ★ 坑：读 core1 的 EDPCSR 把整机挂死

`mw 228120a0 4` 之后网络、telnet、串口全部无响应，串口无 panic 输出，
只能按 RESET。原因推测是这些核 OSLK=1 时外部访问 EDPCSR 返回总线错误，
在本 SoC 上表现为总线挂死。**没有先解 OS Lock 不要再读其他核的
EDPCSR / 调试寄存器**（DEVTYPE、EDPRSR 读是安全的，已验证）。

## 每核中断计数：CPU1 在当前版本上已不复现（12:25 镜像）

临时诊断（标 K7DIAG，事后撤）：`nuttx/arch/arm64/src/common/arm64_gicv2.c`
的 `arm64_decodeirq` 按核数 SGI/PPI/SPI/1023；`k7diag cpus [test]` 打印并
隔 1 秒求差；`test` 建绑 CPU1 的 detached 线程，只等 2 秒标志位；
`k7diag cpus pin <pid> <掩码>` 改亲和性（nsh 没有 taskset）。
镜像 FIT sha 358d99be…（nuttx.bin da05bfeb…），绕行 `kickpi_avoid_cpu1` 仍在。

| 测试 | 结果 |
|---|---|
| 空闲时计数 | 只有 CPU0 收定时器 PPI 27（1001/秒）；CPU1/2/3 全 0 —— SMP 副核平时本就不收中断，计数本身分不出好坏 |
| `cpus test` × 9（中间 `ampctl exec` 动 Linux） | 9/9 线程 100ms 内在 CPU1 跑，CPU1 收到调度 SGI |
| lpwork(5)、kickpi_ui(15) 只绑 0x2，再触发 `/tmp/k7-ask` | 拍照 → JPEG 170115 字节 → HTTPS 全程打 `[CPU1]`，无卡住；CPU1 稳定每秒 35 个 SGI |
| `reboot` × 3，每次 `cpus test` × 2 | 6/6 通过，每次 Linux 在跑（uptime ~31s） |

~~结论：不复现~~ —— **这个结论是错的**，见下一节。绕行还在，测的是
“启动窗口里没人投给 CPU1 之后”的 CPU1，当然正常。

顺带发现：视觉 / 播报接口返回 **HTTP 401 Invalid API Key**，
本地 `app/kickpi_ui/k7_agent_key.h` 的 Key 需要更新（与 CPU1 无关）。

## 根因：启动时丢一个调度 SGI，NuttX 不补发

去掉绕行（12:45 镜像）后立刻复现：CPU0/2/3 正常，绑 CPU1 的线程停在
Ready、CPU1 IDLE 一直 Running；`k7diag` 进程也退不掉（退出要先结束这个
永远不跑的线程 —— 9 月 `k7diag cpus test` 卡 nsh 就是这个）。

| 观察 | 读数 |
|---|---|
| `g_delivertasks`（0x4a6f0178，每核 4 字节） | CPU0/2/3 = 0，**CPU1 = 1（SWITCH_HIGHER）** |
| 手动 `mw 2a701f00=20001`（GICD_SGIR：接口 1、SGI1） | 标志立即清零，卡住的线程跑完，进程退出；之后四核全过 |

机制：`nxsched_deliver_task()`（sched/sched/sched.h）在
`g_delivertasks[目标] == 本次优先级` 时认为中断已在路上，**不再发 SGI**。
丢一个就永远卡住。CPU1 本身没坏。

丢的时刻：补发计数显示每次启动**恰好 1 次**，在开机 2259–2265ms，
5 次启动都一样。与 Linux 早期 `gic_dist_init()`（关 GICD_CTLR 再重配
共享分发器）的时间吻合；“分发器关闭期间写 GICD_SGIR 被丢弃”未单独验证。
副核 GIC 初始化（`arm_gic_initialize`）不清 pending，排除。

## 修复

1. `chip/rk3576/rk3576_smp.c`（新）：CPU0 每 100ms 查各核 `g_delivertasks`，
   连续两次非 NONE 就 `up_send_smp_sched()` 补发。多发无害（处理函数取到
   NONE 不动作）。`board_late_initialize` 启动；`k7diag cpus` 打印补发次数
   和最后一次时刻。
2. 去掉 `kickpi_avoid_cpu1` 绕行。
3. **连带暴露的竞争**：CPU1 能干活后网络起不来（eth0 DOWN / 0.0.0.0，4/4 次）。
   nsh 的 netinit 在 `board_app_initialize` 返回后立刻跑，eth0 却要等 `gmac`
   线程忙等 2.5 秒才注册。以前是三个核被优先级 100 的忙等线程占满，优先级 80
   的 netinit 被饿到 eth0 之后 —— 碰巧对。改为关 `CONFIG_NSH_NETINIT` /
   `CONFIG_NETINIT_THREAD`，由 `gmac_bringup_thread` 注册 eth0 后同步调
   `netinit_bringup()`（amp、amp-dual 两份 defconfig）。
4. 撤掉 NuttX `arm64_gicv2.c` 里的 K7DIAG 计数；`k7diag cpus [核号]` 和
   `cpus pin` 保留。

验证（FIT 写入 17:14Z，nuttx.bin 7ffdde10…）：5 次启动网络自动起来、
四核全过、每次补发 1 次。压力测试结果见下。

## 压力测试（10 分钟）

每轮：`/tmp/k7-ask`（拍照 + JPEG + HTTPS，视觉因 Key 401 失败但前段照跑）、
`/tmp/k7-rec`（录 5 秒）、`ampctl exec uptime`、`k7diag cpus`（逐核），
8 秒后 `/tmp/k7-play`。共 18 轮，**0 失败**；补发计数全程保持 1（运行期
未再丢 SGI）；结束时无 Ready 卡住的任务，`/tmp/k7-vision.jpg` 260380 字节、
`/tmp/k7-rec.wav` 480044 字节。
